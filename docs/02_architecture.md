> 게임 라이브러리를 기록하고 분석하는 모바일 앱

- **작성자**: 사공민규
- **버전**: v0.1 (초안)
- **관련 문서**: 요구사항 정의서(01), 데이터 모델(ERD)

## 1. 전체 구조

```
┌──────────────────────────────┐
│      React Native 앱          │
│      (Android)               │
│                              │
│  · 화면 렌더링                  │
│  · 토큰 보관 및 첨부             │
│  · 입력값 1차 검증               │
└──────────────┬───────────────┘
               │
               │  HTTPS / JSON
               │  Authorization: Token <값>
               ↓
┌──────────────────────────────┐
│    Django + DRF 서버          │
│                              │
│  · 인증 / 권한 검사             │
│  · 비즈니스 로직 (지표 계산)      │
│  · ORM으로 DB 접근             │
│  · Steam API 호출 (M5)        │
└──────┬────────────────┬──────┘
       │                │
       │ SQL            │ HTTPS (M5)
       ↓                ↓
┌─────────────┐   ┌──────────────────┐
│  MariaDB    │   │  Steam Web API   │
│             │   │  (외부)           │
└─────────────┘   └──────────────────┘
```

**핵심 원칙: 앱은 화면만, 서버는 판단만.**

가성비 점수, 방치일수, 완주율 같은 계산은 전부 서버에서 한다.
앱은 받은 숫자를 표시할 뿐이다. 계산식이 바뀌었을 때 앱을
재배포하지 않아도 되고, 나중에 웹 클라이언트가 추가돼도
같은 결과를 보장할 수 있다.

## 2. 컴포넌트별 역할

### 2.1 React Native 앱

| 항목 | 내용 |
|---|---|
| 역할 | 사용자 인터페이스 전담 |
| 하는 일 | 화면 그리기, 입력 받기, API 호출, 토큰 보관 |
| 하지 않는 일 | 통계 계산, 중복 판별, 데이터 정규화 |

입력값 검증은 앱에서도 하고 서버에서도 한다. 앱 쪽 검증은
**사용자 편의**(즉시 피드백)를 위한 것이고, 서버 쪽 검증이
**실제 방어선**이다. 앱은 얼마든지 우회될 수 있으므로
서버 검증을 생략하지 않는다.

### 2.2 Django + DRF 서버

| 항목 | 내용 |
|---|---|
| 역할 | 인증, 데이터 저장, 계산, 외부 API 중계 |
| Django | 인증, ORM, 관리자 페이지 |
| DRF (Django REST Framework) | REST API 생성, 직렬화, 권한 제어 |

**Django와 DRF의 관계**

Django만으로는 HTML 페이지를 반환한다. 모바일 앱은 HTML이 아니라
JSON이 필요하므로, Django 위에 DRF를 얹어 JSON API 서버로 만든다.
DRF는 Django를 대체하는 것이 아니라 그 위에 씌우는 층이다.

### 2.3 MariaDB

| 항목 | 내용 |
|---|---|
| 역할 | 데이터 영구 저장 |
| 접근 방식 | Django ORM 경유. 직접 SQL은 복잡한 집계 쿼리에만 사용 |

### 2.4 Steam Web API (M5, 외부)

| 항목 | 내용 |
|---|---|
| 역할 | 사용자의 게임 목록과 플레이타임 제공 |
| 호출 주체 | **서버.** 앱이 직접 호출하지 않는다 |

**앱이 직접 호출하지 않는 이유**

Steam API 키를 앱에 넣으면 앱을 뜯어보는 것만으로 키가 노출된다.
서버가 키를 보관하고 대신 호출하면 키는 서버 밖으로 나가지 않는다.
호출 횟수 제한도 서버에서 한 곳으로 통제할 수 있다.

## 3. 기술 선택 근거

### 3.1 백엔드: Django (vs FastAPI)

이전 프로젝트(PulseGrid)에서 FastAPI를 사용했으므로,
같은 것을 반복하지 않고 다른 접근을 경험하기 위해 Django를 선택했다.

| 항목 | Django | FastAPI |
|---|---|---|
| 인증 | 기본 내장 (회원가입, 해싱, 세션) | 직접 구현 |
| ORM | 기본 내장 | 별도 라이브러리(SQLAlchemy) |
| 관리자 페이지 | 기본 내장 | 없음 |
| 실시간 통신 | 별도 설정 필요 | 기본 지원 |
| 학습 곡선 | 가파름 (구조가 정해져 있음) | 완만함 |

**이 프로젝트에는 Django가 맞는 이유**

1. 인증이 핵심 요구사항(F-01)인데, 인증은 직접 구현하면
   보안 사고가 나기 쉬운 영역이다. 검증된 구현을 쓰는 편이 안전하다.
2. 실시간 통신이 필요 없다. FastAPI의 최대 강점이 여기서는 무의미하다.
3. 관리자 페이지로 초기 데이터(장르 목록 등)를 손쉽게 입력할 수 있다.

> PulseGrid는 2초 간격 실시간 브로드캐스트가 핵심이라 FastAPI가 맞았다.
> 프레임워크에 우열이 있는 게 아니라 문제의 성격이 다르다.

### 3.2 프론트엔드: React Native (vs Flutter)

학교 캡스톤(Surbi)에서 Flutter를 사용 중이므로,
다른 크로스플랫폼 접근을 경험하기 위해 React Native를 선택했다.

| 항목 | React Native | Flutter |
|---|---|---|
| 언어 | JavaScript | Dart |
| 렌더링 | 네이티브 컴포넌트 사용 | 자체 렌더링 엔진 |
| 학습 연계 | 학과 JavaScript 수업과 직결 | 별도 언어 학습 필요 |

**모바일이어야 하는 이유**

이 앱의 사용 시나리오는 "PC 앞이 아닐 때"에 몰려 있다.
할인 소식을 보고 살지 말지 판단할 때, 친구와 얘기하다 위시리스트에
추가할 때, 뭘 할지 정할 때 — 전부 PC를 켜기 전이거나 밖이다.
웹 대시보드였다면 이 시나리오가 성립하지 않는다.

### 3.3 데이터베이스: MariaDB (vs SQLite)

| 항목 | MariaDB | SQLite |
|---|---|---|
| 형태 | 서버 프로세스 | 파일 하나 |
| 동시 접속 | 강함 | 약함 |
| 적합한 상황 | 여러 사용자가 붙는 서버 | 혼자 쓰는 로컬 도구 |

PartScope는 혼자 쓰는 콘솔 도구라 SQLite가 맞았지만,
이번에는 다중 사용자를 전제로 하므로 MariaDB를 쓴다.
학과 커리큘럼에서 다루는 DBMS이기도 하다.

## 4. 인증 흐름

토큰 기반 인증을 사용한다.

```
[회원가입]
앱 → POST /auth/register (username, email, password)
    → 서버: 비밀번호 해싱 후 저장
    ← 성공 응답

[로그인]
앱 → POST /auth/login (username, password)
    → 서버: 해시 비교
    ← 토큰 발급

[이후 모든 요청]
앱 → GET /entries
     Authorization: Token abc123...
    → 서버: 토큰으로 사용자 식별
    → 그 사용자의 데이터만 조회
    ← 결과
```

**토큰 방식을 쓰는 이유**

세션 방식은 브라우저의 쿠키에 의존한다. 모바일 앱에는 브라우저가 없으므로
토큰을 직접 보관했다가 요청 헤더에 붙이는 방식이 자연스럽다.

**사용자별 데이터 격리**

모든 조회는 토큰에서 얻은 사용자로 자동 필터링한다.
앱이 다른 사용자의 `entry_id`를 요청해도 조회되지 않아야 한다.
DRF의 권한 클래스와 쿼리셋 필터를 함께 사용해 이중으로 막는다.

## 5. Steam 동기화 흐름 (M5)

```
1. 앱: "동기화" 버튼 누름
        ↓
2. 서버: 사용자의 steam_id로 Steam API 호출
        ↓
3. 응답: 보유 게임 목록 + 각 게임의 총 플레이타임(분)
        ↓
4. 게임별로 처리:
     ├─ steam_appid가 games에 있음  → 기존 game_id 사용
     └─ 없음                        → games에 새로 추가
        ↓
5. entries 확인:
     ├─ 기록 없음                   → 새로 생성 (source='STEAM')
     ├─ source='STEAM'             → 플레이타임만 갱신
     └─ source='MANUAL'            → 건드리지 않음
        ↓
6. 앱: 결과 요약 표시 (추가 N개 / 갱신 M개)
```

**동기화를 수동 트리거로 두는 이유**

자동 주기 호출은 Steam의 호출 제한에 걸릴 위험이 있고,
사용자가 앱을 안 쓰는 동안 불필요한 요청이 계속 나간다.
버튼을 눌렀을 때만 호출하면 제한 관리가 단순해진다.

## 6. 프로젝트 구조 (예정)

```
playledger/
│
├── server/                    # Django 프로젝트
│   ├── config/                # settings, urls
│   ├── accounts/              # 인증 앱
│   ├── library/               # 게임/보유기록 앱
│   ├── manage.py
│   ├── requirements.txt
│   └── .env.example
│
├── app/                       # React Native
│   ├── src/
│   │   ├── screens/
│   │   ├── components/
│   │   ├── api/               # API 호출 모듈
│   │   └── navigation/
│   ├── package.json
│   └── app.json
│
├── docs/
│   ├── 01_requirements.md
│   ├── 02_architecture.md
│   ├── 03_api_spec.md         # M1 이후 작성
│   ├── 04_ui_design.md
│   ├── 05_milestones.md
│   ├── ERD.md
│   └── DEVLOG.md
│
├── .gitignore
├── LICENSE
└── README.md                  # M4 이후 작성
```

**API 호출을 `api/` 모듈로 모으는 이유**

화면마다 `fetch`를 직접 호출하면, 서버 주소가 바뀌거나 토큰 첨부 방식이
바뀔 때 모든 화면을 고쳐야 한다. 호출을 한 곳에 모아두면 그 파일만
고치면 된다. PulseGrid에서 수집기 설정을 `config.json`으로 분리한 것과
같은 발상이다.

## 7. 설정 및 비밀값 관리

| 항목 | 보관 위치 | Git 추적 |
|---|---|---|
| Django SECRET_KEY | `server/.env` | X |
| DB 접속 정보 | `server/.env` | X |
| Steam API 키 | `server/.env` | X |
| 서버 주소 (앱) | `app/src/api/config.js` | O (개발용 기본값) |

`.env.example`에 키 이름만 적어두고 값은 비워서 커밋한다.
처음 클론한 사람이 무엇을 채워야 하는지 알 수 있게 한다.
