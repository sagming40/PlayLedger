## 1. 일정 수립 전제
 
| 항목 | 내용 |
|---|---|
| 개발 형태 | 1인 개인 프로젝트 |
| 병행 상황 | 한국폴리텍II대학 하이테크과정 재학 중 (~2026.12.18), 캡스톤(Surbi) 병행 |
| 가용 시간 | 주당 약 5~8시간 (PulseGrid 때보다 적게 잡음) |
| 일정 단위 | 주차(Week) 기준. 특정 날짜 고정하지 않음 |
| 릴리즈 목표 | M4 완료 시점을 v1.0으로 정의 |
 
**PulseGrid보다 가용 시간을 낮게 잡은 이유**
 
캡스톤 마감이 다가올수록 학교 작업에 시간이 쏠린다. 낙관적으로 잡았다가
일정이 밀리면 문서가 무의미해지므로, 처음부터 보수적으로 잡고
"계획보다 빨리 끝났다"를 목표로 한다.
 
**새로 배우는 것이 두 개라는 점**
 
Django와 React Native를 동시에 처음 다룬다. 두 개를 한 단계에서
같이 배우면 문제가 생겼을 때 어느 쪽 문제인지 판별하기 어렵다.
따라서 M1(백엔드)을 완전히 끝낸 뒤 M2(앱)로 넘어간다.

## 6. 완료 정의 (Definition of Done)
 
각 마일스톤은 아래를 **모두** 충족해야 완료로 본다.
 
1. 해당 단계의 완료 기준 체크박스가 전부 채워짐
2. 코드가 Git에 커밋되어 있음

4. 임시 코드 / 주석 처리한 실험 코드가 제거됨

## 7. 문서 갱신 규칙
 
- 작업 항목을 완료하면 **그때 바로** 체크한다. 나중에 몰아서 하면 기억이 왜곡된다
- 계획에 없던 작업을 했으면 체크박스를 **추가하고** 체크한다. 지우지 않는다
- 마일스톤 상태(2장 표)는 완료 기준을 전부 충족한 시점에만 ✅로 바꾼다
- 범위를 바꿨으면 변경 이력에 **사유와 함께** 남긴다

> 계획대로 안 된 흔적을 지우지 않는 것이 이 문서의 목적이다.
> 결과만 남은 문서는 결과만 알려주지만, 과정이 남은 문서는 판단 근거를 알려준다.
