# 0002 · RN + Django + MariaDB → Vue 3 + FastAPI + PostgreSQL, 앱 → 반응형 웹

- **상태**: 채택
- **날짜**: 2026-09-18

## 맥락

취업으로 프로젝트 목적이 포트폴리오에서 자기계발 · 취미로 바뀌었다. 함께 준비하던 별도 프로젝트(단축 URL 서비스 '콕')는 기술 스택을 먼저 정하고 주제를 끼워 맞춘 탓에 재미가 없어 접고, 그 스택을 문제의식이 분명한 PlayLedger에 적용했다. 전환 시점의 구현량이 M1 + 네비게이션 골격이라 버리는 비용이 작았다. 이전 버전은 태그 `v0-rn-django`.

## 결정

**백엔드: FastAPI** — v0에서는 인증 · 관리자 페이지가 내장된 Django를 택했다. 목적이 바뀌어 판단도 바뀌었다.

| 관점 | v0 (포트폴리오) | v1 (자기계발) |
|---|---|---|
| 인증 | 검증된 내장 구현이 안전 | **직접 구성하며 원리를 이해**하는 것이 목표 |
| 외부 API 호출 | 드문 작업 | Steam 동기화 · 워커에서 비동기 호출이 잦음 |
| 관리자 페이지 | 초기 데이터 입력에 유용 | HeidiSQL로 대체 가능 |

**프론트엔드: Vue 3** — React 계열은 v0에서 React Native로 맛봤으므로 다른 접근을 경험한다.

| 항목 | Vue 3 | React |
|---|---|---|
| 문법 | HTML에 가까운 템플릿 | JSX (JS 안에 HTML) |
| 상태 관리 | Pinia (공식 권장) | 선택지 다양 |
| 경험 | 처음 | v0에서 React Native로 기초 경험 |

**웹이어야 하는 이유** — v0는 "PC 앞이 아닐 때"를 사용 시나리오로 보고 모바일 앱을 택했다. 다시 따져보면 기록과 분석이 실제로 일어나는 순간은 게임을 막 끝냈거나 Steam을 켜둔 PC 앞이 더 많다. 밖에서 쓰는 시나리오(위시리스트 추가 등)는 반응형 웹으로 모바일 브라우저에서 충분히 대응할 수 있다.

**DB: PostgreSQL** — MariaDB는 이미 여러 번 다뤘으므로 다른 DBMS를 경험한다. HeidiSQL이 PostgreSQL도 지원하므로 "SQL 먼저 검증" 작업 방식은 유지된다.

| 항목 | PostgreSQL | MariaDB |
|---|---|---|
| 비동기 드라이버 | asyncpg (성숙) | 상대적으로 선택지 적음 |
| 날짜 계산 | 날짜끼리 빼면 일수 | `DATEDIFF()` 함수 |
| 경험 | 처음 | 학과 수업, PulseGrid, v0 |

**Redis는 나중에** — v1.0 범위에는 쓰지 않는다. Steam 자동 동기화(M9)에서 작업 큐로 처음 도입한다. 쓸 곳이 생기기 전에 넣으면 구조만 복잡해진다.

**범위 확대 + 버전별 결승선** — 시간 여유가 생겨 위시리스트 · 구매 전 경고 · Steam 자동 동기화 · 플레이 세션 · 추첨 · Discord 로그인을 범위에 넣었다. 마감이 없어진 만큼 "끝이 없어 못 끝내는" 위험을 막으려고 v1.0은 기존 범위(M0 ~ M4) 그대로 두고, 확장은 v1.1 ~ v2.1로 나눴다.

## 검토한 대안

- **v0 스택 유지** — 목적이 바뀌었는데 구현 비용만 아끼는 선택이다. 버릴 구현도 적었다.
- 각 항목의 대안은 위 표와 같다.

## 감수할 것

- 인증을 직접 구성하는 위험이 남는다. 대신 토큰 서명 · 비밀번호 해싱은 검증된 라이브러리를 쓰고 직접 구현하지 않으며, 사용자 격리와 토큰 만료는 pytest로 자동 검증한다.
- Vue와 비동기 SQLAlchemy를 동시에 처음 다룬다. M1을 끝낸 뒤 M2로 넘어가 겹치지 않게 한다 (`PLAN` 1장).
