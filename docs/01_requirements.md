# PlayLedger — 요구사항 정의서

> 게임 라이브러리를 "장부"처럼 기록하고, 사놓고 안 한 게임을 데이터로 관리하는 모바일 앱
>
> 작성일: 2026-08-13 / 상태: v0.2

---

## 1. 개요

### 1.1 왜 만드는가

스팀 세일 때마다 게임을 사지만, 실제로 플레이하는 비율은 그보다 훨씬 낮다.
문제는 "많이 샀다"가 아니라 **내가 얼마나 안 하고 있는지를 모른다**는 것이다.

- "이 게임 산 게 언제였지?"
- "작년에 산 것 중에 아직 시작도 안 한 게 몇 개야?"
- "정가 6만원 주고 산 게임, 결국 2시간 하고 접었으면 시간당 3만원인데?"

라이브러리 목록을 보는 것만으로는 이 질문에 답할 수 없다.
**보유 목록이 아니라 소비 이력을 기록하고, 그걸 숫자로 환산하는 것**이 이 프로젝트의 목적이다.

### 1.2 학습 목표

결과물과 별개로, 이 프로젝트로 익히려는 것:

| 영역 | 목표 |
|---|---|
| Django | 웹 프레임워크 구조 이해, ORM, DRF로 REST API 설계 |
| 인증 | 회원가입/로그인, 토큰 기반 인증, 사용자별 데이터 격리 |
| React Native | 모바일 UI 구성, 화면 전환, API 연동, 상태 관리 |
| 외부 API | Steam Web API 연동, 외부 데이터와 로컬 데이터 병합 |
| DB 설계 | 다대다 관계, 정규화, 사용자-데이터 관계 모델링 |

### 1.3 기존 프로젝트와의 관계

| 프로젝트 | 성격 | 이번에 새로 하는 것 |
|---|---|---|
| PulseGrid | 실시간 모니터링 / FastAPI / 웹 | — |
| PartScope | 배치 분석 / SQLite / 콘솔 | — |
| **PlayLedger** | **기록·분석 / Django / 모바일** | **인증, 모바일 앱, 외부 API 연동** |

세 프로젝트 모두 **"감으로 하던 판단을 숫자로 바꾼다"**는 문제의식을 공유한다.

## 2. 용어 정의

| 용어 | 정의 |
|---|---|
| 게임(Game) | 게임 자체의 정보. 제목, 장르, 플랫폼 등. 모든 사용자가 공유하는 마스터 데이터 |
| 보유 기록(Entry) | 특정 사용자가 특정 게임을 소유한 기록. 구매일, 구매가, 상태, 평점 등 |
| 백로그(Backlog) | 구매했으나 아직 시작하지 않은 게임 |
| 방치일수 | 구매일로부터 오늘까지의 일수 (상태가 '미시작'인 경우에만 의미 있음) |
| 시간당 비용 | 구매가 ÷ 총 플레이타임. 낮을수록 본전을 뽑은 것 |
| 사장률 | 전체 보유 게임 중 플레이타임 1시간 미만인 게임의 비율 |

## 3. 범위

### 3.1 하는 것

- 게임 보유 기록의 등록 / 조회 / 수정 / 삭제
- 진행 상태 관리 및 상태별 필터링
- 평점 및 한줄평 기록
- 보유 현황 통계 및 백로그 분석
- 회원가입 및 로그인 (사용자별 데이터 분리)
- Steam 라이브러리 자동 동기화 (M5)

### 3.2 하지 않는 것 (Out of scope)

| 항목 | 이유 |
|---|---|
| 게임 추천 알고리즘 | 범위가 급격히 커지고, 이 프로젝트의 문제의식과 무관 |
| 소셜 기능 (친구, 공유, 댓글) | 핵심 문제 해결에 불필요 |
| 게임 구매 / 가격 비교 | PartScope와 성격이 겹침 |
| 웹 프론트엔드 | 모바일 앱으로 충분. 필요 시 DRF 기본 화면으로 대체 |
| iOS 빌드 및 배포 | 맥 환경 필요. 안드로이드 우선 |

### 3.3 나중에 검토 (지금은 안 함)

- 다른 플랫폼 연동 (Epic, GOG, PlayStation)
- 플레이 세션 단위 기록 ("오늘 2시간 했음")
- 게임 이미지/스크린샷 저장

## 5. 핵심 계산식

### 5.1 시간당 비용

```
시간당 비용 = 구매가(원) ÷ 총 플레이타임(시간)
```

낮을수록 본전을 뽑은 것. 플레이타임이 0인 경우 계산하지 않고 `-`로 표시한다.

> 예시
> - 게임 A / 66,000원 / 40시간 → 1,650원/시간
> - 게임 B / 66,000원 / 2시간 → 33,000원/시간

### 5.2 사장률

```
사장률 = (플레이타임 1시간 미만 게임 수 ÷ 전체 보유 게임 수) × 100
```

### 5.3 완주율

```
완주율 = (클리어 상태 게임 수 ÷ (전체 - 미시작)) × 100
```

**분모에서 미시작을 제외하는 이유:** 시작도 안 한 게임을 "완주 실패"로 세면
게임을 살수록 완주율이 떨어지는 이상한 지표가 된다. 완주율은
"시작한 것 중 끝낸 비율"이어야 의미가 있다.

### 5.4 지표 해석 주의

이 숫자들은 **판단 보조용이지 평가가 아니다.**
30시간짜리 게임을 5시간만 하고 접었어도 그 5시간이 즐거웠으면 그걸로 된 것이다.
지표는 "내가 어떤 패턴으로 게임을 사고 있는가"를 보여주는 용도이고,
구매 결정은 사람이 한다.

## 6. 데이터 모델 초안

> 상세 ERD는 `docs/ERD.md`에서 별도 작성

### 6.1 주요 테이블

| 테이블 | 역할 |
|---|---|
| `users` | 사용자 계정 (Django 기본 인증 모델 활용) |
| `games` | 게임 마스터 데이터 (제목, 출시일, steam_appid) |
| `genres` | 장르 |
| `game_genres` | 게임-장르 다대다 연결 |
| `entries` | 사용자별 보유 기록 (구매일, 구매가, 상태, 평점, 플레이타임) |

### 6.2 설계 판단

**`games`와 `entries`를 나누는 이유**

같은 게임을 여러 사용자가 보유할 수 있다. 게임 제목과 장르를 사용자마다
중복 저장하면 데이터가 낭비되고, 게임 정보를 고칠 때 모든 행을 고쳐야 한다.
게임 자체의 정보(`games`)와 "내가 언제 얼마에 샀고 얼마나 했는지"(`entries`)를
분리하면 이 문제가 사라진다.

**상태(status) 값**

`BACKLOG` (미시작) / `PLAYING` (플레이중) / `CLEARED` (클리어) /
`ON_HOLD` (보류) / `DROPPED` (포기)

'보류'와 '포기'를 나누는 이유는 백로그 분석 대상이 다르기 때문이다.
보류는 언젠가 돌아올 게임이고, 포기는 이미 끝난 게임이다.

## 7. 비기능 요구사항

| 항목 | 요구사항 |
|---|---|
| 성능 | 게임 200개 기준 목록 조회 1초 이내 |
| 보안 | 비밀번호는 평문 저장 금지 (Django 기본 해싱 사용) |
| 인증 | 토큰 기반. 다른 사용자의 데이터는 조회 불가 |
| 개인정보 | Steam ID 외의 개인정보는 수집하지 않음 |
| 설정 관리 | API 키, DB 비밀번호는 Git에 올리지 않음 (`.env` 또는 별도 설정 파일) |
| 대상 환경 | Android 우선. 개발 중에는 에뮬레이터 및 실기기 테스트 |

## 9. 마일스톤

| 단계 | 내용 | 완료 기준 |
|:---:|---|---|
| M0 | 환경 구성 | Django + MariaDB 연결 확인, RN 빈 화면 실행 확인 |
| M1 | 인증 + 게임 CRUD (백엔드) | DRF 화면에서 회원가입/로그인/게임 등록이 전부 동작 |
| M2 | RN 화면 연동 | 앱에서 로그인하고 목록 조회 및 등록 가능 |
| M3 | 상태 관리 + 평점 | F-04, F-06, F-07 완료 |
| M4 | 통계 대시보드 (**v1.0**) | F-08 ~ F-11 완료. 여기까지가 작동하는 완성품 |
| M5 | Steam API 연동 | F-12 완료. 자동 수집 데이터와 수동 데이터가 충돌 없이 병합 |
| M6 | 문서화 및 정리 | README, API 명세, 스크린샷, DEVLOG 정리 |

**M4까지가 v1.0이다.** Steam 연동 없이도 완결된 앱이어야 하고,
M5는 그 위에 얹는 확장이다. 순서를 이렇게 잡은 이유는
M5에서 막히더라도 보여줄 수 있는 결과물이 남기 때문이다.
